# ROADMAP.md — 開発Phase計画

各Phaseは「完了条件」を満たしてから次へ進む。Phase内で全機能を作り切らずに
次のPhaseへ進むことは禁止（最重要方針#1〜4）。各Phase終了時は
`docs/PHASE_REPORTS/PhaseN.md`（またはこのファイルの更新）で以下を報告する:

```
完了したこと / 追加したファイル / DB変更 / テスト結果 /
現在動作する機能 / 未完成 / 既知の問題 / 次Phase
```

計画していたPhase(0〜11)はすべて完了している。全Phase横断の要約と、
実運用前に必要な残作業の一覧は `docs/FINAL_REPORT.md` を参照(Phase12
以降の追加は同レポートには未反映)。

## Phase 9 — Export 【完了】

引き続き使う方針。詳細と理由: `docs/EXPORT.md`4章。

## Phase 11 — 高度機能（初期販売版には必須ではない）【Command Paletteのみ完了】

Command Palette(Ctrl+K / Cmd+K): 作品一覧・章・ワークスペースの各
セクションへキーボードだけでジャンプできる検索付きパレット。トップバー
の「コマンド(Ctrl+K)」ボタンからも開ける。既存機能への新しい到達手段を
追加するのみで、新しいデータや機能そのものは増やさない設計
(`src/features/commandPalette/CommandPalette.tsx`)。

以下は仕様書自身が「初期販売版には必須ではない」と明示している高度機能
であり、意図的にこのプロジェクトのスコープ外とする: Semantic Search
(埋め込みベクトル検索基盤が必要) / Map(地図機能) / Custom templates /
Plugin architecture / Local AI(オンデバイスLLM) / Cloud sync /
Multi-device / Collaboration(複数人同時編集)。理由: いずれも現在の
ローカルSQLite単体構成を前提としたアーキテクチャの大幅な変更
(サーバー基盤・同期プロトコル・権限モデル・ベクトルDB等)を要し、
「データ安全性 > 執筆体験 > 安定性」を優先する本アプリの現段階の方針
(CLAUDE.md)とも、既存の安定した機能を壊さず段階的に拡張するという
これまでの開発方針とも整合しない。将来これらに着手する場合は、
専用の設計ドキュメントを新設したうえで独立したPhaseとして計画すべき。

## Phase 15 — Auto Update 【完了(GitHub上での実配信検証待ち)】

ユーザーから「アップデートのたびに手動で入れ直すのが面倒。自動で更新を
探しに行く本格的な機能が欲しい」との要望を受けて着手。Phase10で「この
サンドボックスでは検証も安全な実装もできない」として意図的に見送って
いた機能だが、ユーザーが実機(Windows PC)を持ち配布先としてGitHub
Releasesを選べる状況になったため、コード実装自体はサンドボックス側で
完成させ、実際の署名・配信・検証はユーザーのGitHubリポジトリ上で行う
方針とした。

1. `tauri-plugin-updater` + `tauri-plugin-process`を導入し、起動時の
   自動確認(見つかった場合のみバナー表示)と「このアプリについて」から
   の手動確認の2経路を用意。ダウンロード・適用・再起動は必ずユーザーの
   明示操作(「今すぐ更新」ボタン)を経てから実行し、執筆中に無断で
   再起動されることがないようにした(CLAUDE.md優先順位#1「データ安全性」
   を最優先した設計)。
2. Ed25519署名鍵ペアを生成し、公開鍵のみ`tauri.conf.json`に埋め込み。
   秘密鍵はリポジトリに含めず(`.gitignore`で遮断)、ユーザー本人にのみ
   別途受け渡した。
3. GitHub Actions(`tauri-apps/tauri-action`)によるリリース自動化
   ワークフローを用意し、タグpushだけで署名付きインストーラ・
   `latest.json`・GitHub Release下書きが自動生成されるようにした
   (ユーザーが手元のPCで毎回ビルドし直す必要をなくすことが主目的)。
4. 設計判断・署名鍵の取り扱い・実際のリリース手順(GitHub Actions版/
   手動ビルド版の両方)を`docs/UPDATE_RELEASE.md`にまとめた。

追記(2026-09-19): ユーザーが実際に`v0.1.0`タグをpushし、
`release.yml`ワークフローの実行→(署名パスワードSecretの設定ミス
による1回目の失敗→原因特定→Secret削除で再実行→成功)→GitHub
Releaseの「Publish release」までを実機で完了した。ビルド・署名・
Release公開の流れは実際に動作することを確認済み(詳細・つまずいた
点の記録は`docs/UPDATE_RELEASE.md` 5章)。既知の制約: `tauri.conf.
json`の配信エンドポイントは`https://github.com/satoyu100match-star/
novel-studio-ai/releases/latest/download/latest.json`に確定・稼働
済みだが、既存インストール済みアプリが実際に「新バージョンがある」
と検知してダウンロード・適用・再起動できることの確認は、次に
バージョンを上げて(例: v0.1.1)リリースした時点で行う(現時点では
比較対象となる新バージョンがまだ存在しないため)。

## Phase 16 — 単一ペインセクションのスクロール不具合修正 【完了】

ユーザーから「エクスポート画面の下部の案内文が、スクロールバーも無く
途中で見切れている」との報告(スクリーンショット付き)を受けて調査。
Phase13で修正した「追加」ボタンの横方向のテキスト切れ(`.field-row`の
flex-shrink不足)とは別の原因で、今回は縦方向: Character/World/
Story/AI/分析/資料・メモ/ゴミ箱/エクスポートの全セクションに共通する
親コンテナ`.workspace__body--single`に`overflow-y: auto`が
指定されておらず、内部で独自のスクロール領域を持たないパネル
(`.detail-form`/`.card`を直接置いているエクスポート・ゴミ箱・人物
相関タブなど)では、画面の高さを超えた内容が見た目上切れるだけで
スクロールする手段が無かった。

この共通の親コンテナ1箇所に`overflow-y: auto`を追加するだけで、
個々のパネルを1つずつ直す必要なく解消した(AI/分析セクションの内側
ラッパーや各種リスト`.entity-list`/`.timeline-list`/`.todo-list`等、
既に自前でスクロールを持つ構成には影響しない設計)。調査時に、同じ
`.workspace__body--single`配下の他セクション(人物相関タブ・時系列・
TODO等)についても同様の切れが起きうる構成かどうかを一通り確認し、
今回の1箇所の修正で横断的に解消されることを確認した。

## Phase 17 — AIキーのOS資格情報ストア連携(0.1.1) 【完了】

Auto Update(Phase15)の実地テストとして「バージョンを上げて再度
リリースする」ための題材を探していたところ、AI設定画面に表示している
「APIキーはアプリ実行中のみメモリ上に保持され、再起動すると再入力が
必要」という既知の制約(Phase5からの技術的負債として明記していたもの)
を解消してほしいとの依頼を受けた。

Phase5時点ではこの開発環境からcrates.ioへの新規クレート取得ができず
`keyring`クレートを導入できなかったが、Phase9で既にネットワーク制約が
解消していたことが判明していた(EPUB/PDF向けの`zip`/`printpdf`追加で
確認済み)。そこで、CLAUDE.md/docs/AI.mdに「解消次第、最優先で置き換え
ること」と明記していた通り、`keyring`クレート(Windows Credential
Manager / macOS Keychain / Linux Secret Service)へ実際に置き換えた。
自前の暗号化コードは書かず、各OSの既存の安全な仕組みにそのまま委ねる
方針を貫いている。資格情報ストアが使えない環境では、保存・読み込みの
失敗をログに警告として記録した上でセッション中のみメモリで動作を
継続し、AI機能やアプリ自体を止めないフォールバックにした。

あわせて、この変更を含む`v0.1.1`としてバージョンを上げ、Phase15で
